# Saya 原型撰写

## 先判断这轮要交什么

按用户本轮的明确要求和停点处理；已有确认稿从当前阶段接着做。多个交付物按用户给的顺序分别处理，不自动启动后续阶段。

1. **直接写需求、评审或局部改稿**：用下面的写稿规范。已有原型或能讲清需求方向即可开始；只讨论一个入口的位置，就只给建议。只评审时说明问题和修改建议，不代改原文。局部改动只改指定范围，指出受影响但未授权修改的内容。
2. **从想法一起做原型，或者指定出线框、视觉稿**：读 [原型协作](references/prototype-collaboration.md) 的相关阶段。先搞清当前 Saya 界面、保留区和改动区；从确认过的阶段继续。写开发逻辑时回到本文件。
3. **多语言翻译或后台上传表**：完整读 [多语言翻译](references/multilingual-translation.md)。若只是讨论命名、提取或预览文案，只给文字。不要因为文案属于新需求就开原型流程。
4. **只录入、更新或回查已确认的 TAPD 需求**：直接读 [原型协作](references/prototype-collaboration.md) 的「TAPD 交付」小节；不重画、不擅改正文。仅阅读或评审 TAPD 需求不触发交付。

版本规划和上线效果评估不按原型流程处理。内容确认不等于授权提交 TAPD、发布预览或归档。只在用户授权、环境允许的范围内执行外部操作；结果未核实，不报完成。

## 核对产品现状

- 以用户最新明确确认的范围和决策为准。现有功能优先核对当前端截图／录屏、团队维护的功能说明、获准访问的 Figma 或 TAPD。区分线上现状、已确认待开发方案、历史稿、竞品、示意稿和待确认项。来源冲突时指出冲突及其影响，不替产品定口径。
- 不依赖任何个人知识库或历史会话。底图或链接不可读时先做能核实的部分；只请求会改变实现或布局的那份资料。不读取和整理无关素材，不把看不到的内容写成事实。
- 确认过的规则、文案、稿件结构和编号优先复用。跨会话先看最新交接及可访问产物，不重新向用户确认已有明确依据的决定。

## 写开发逻辑

目标是让开发不用看讨论历史，也能实现同一个结果。图能说明布局，不能代替触发、配置、状态和异常规则。

- **按模块写**：围绕用户任务或后台配置对象拆模块。只对未确认部分逐块讨论；收到合稿请求后合并确认过的模块，共用规则写在一个归属位置。背景按原因分点，只有影响本期的内容才写。正文只写最终态，不夹带旧方案和已否决内容。
- **按场景写**：在涉及的场景里写清用户／角色、入口和触发条件、展示条件及内容、操作和结果、返回去向及适用的异常。用短标题和嵌套列表把条件、状态及结果分开。图放在对应文字旁边，不复述图上显然可见且无行为意义的细节。
- **按状态查**：针对实际涉及的功能检查权限、空态、失败、失效、重复操作、跨入口一致性与同步。弹窗写清何时弹、频控、优先级、关闭后行为和重新进入；涉及计数、奖励或权益时检查重复发放、并发、失败处理和状态刷新。关系功能区分自己和他人视角；多种关系同时适用时，写明建立、解除、联动和展示优先级。只覆盖与本次需求有关的分支。
- **写清复用与配置**：说明复用哪个入口或能力、继承什么行为。涉及数值时先写流程，再讲参数含义、单位、首期值、配置归属、生效范围，最后写计算、上下限含不含本数及必要示例。区分产品规则、UI 打样值与待研发核验项。支付、奖励等规则要清楚说明条件和用户保护，不用模糊口径或误导性展示。
- **后台按对象和生命周期写**：说明配置对象、权限、创建／编辑、可改字段、校验、生效与撤回。沿用现有表单只新增选项，可用文字说明；复杂新增交互才画图。批量导入写清列名、必填和默认值、校验失败提示、部分成功的处理。只读核对后台不代表授权改配置。
- **按范围交付**：实现关键规则未定，标「待确认」并说明只影响哪块；可独立完成的部分继续做。埋点、数据回收和联调清单仅在本次要求时加入；涉及数据时按需要组织交互、功能、效果数据，不强塞三类。只做文字或文案时，用用户要求的格式。

合稿检查：逐模块核对已确认规则、对应图、链接和参数。同一个数字出现在不同规则里，不代表同一个参数。局部改动只回查受影响的产物。必交图、正式链接或关键规则未齐，不标全部交齐；经用户同意延期的项要明示。

## 归档

仅在需求内容确认且用户授权后，写入其指定的团队知识库或目录。以已回查的 TAPD 正文或用户指定的确认稿为准；保存标题、版本、状态、来源、正文与表格、按原顺序嵌入的原图、约定附件与预览链接，讨论单独留追溯入口。整理后核对附件数量、引用和索引，缺失项逐项标注，不拿聊天草稿代替 TAPD 终稿。已有记录不擅自覆盖；未指定归档位置时先确认，不另建替代知识库。归档不代表功能上线。
