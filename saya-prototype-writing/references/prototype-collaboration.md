# Saya 原型协作

**对齐目标和范围 → 核对 Saya UI 底稿 → 确认线框和关键文案 → 出视觉稿（按需做模拟器）→ 分模块写逻辑 → 合稿自检与确认 → 按授权交付、回查、归档。**

按本轮任务的起点和停点使用。产品确认范围、关键布局及业务规则；AI 负责整理材料、出图、写稿和一致性检查。只做 TAPD 时跳到末尾「TAPD 交付」。

## 1. 先拆范围

- 从一个简短目标、现有材料或口述开始。给出目标用户与场景、本期做／不做、预计模块和页面、会改变设计的待定问题。不要要求产品先画一整套原型。
- 说明哪些是新增、哪些复用、哪些未知。模块确认后优先推进下一步，不把所有非阻塞细节都变成开工前的问题。

## 2. 核对 Saya UI 底稿

- 优先使用符合版本、平台、页面状态和用户角色的当前端截图或录屏、团队底图库，或能访问的 Figma 对应画板；历史需求和竞品只能作为参考。截图能证明布局，不能单独证明控件的完整交互；用已确认规则互证。
- 每个待出图场景先说清：入口和状态、底稿来源、现有控件布局、要保留的区域和交互、这次只改哪里、有什么证据缺口。常见需校对的包括顶部信息、底部操作区、列表层级、弹层遮挡和返回路径；不要用组件模板擅自重排。
- 缺底稿时可出明确标注的结构示意。只缺那一页或那一状态就只索取它；不能核对当前界面时，不把历史底图或 AI 稿标成当前实况。已有界面只拿得到历史图时，经产品接受可做探索稿；拟交付的视觉稿应有可校对的当前底稿。全新页面可基于已确认线框与同类 Saya 组件制作。

## 3. 确认线框，再出视觉

- 线框标清区域、控件和位置、信息顺序、主要动作、跳转和代表性状态。需要确认的关键文案在这一步一起对齐；如本轮只要线框，到此停止。
- 布局与关键动作确认后出视觉稿。保留未改区域、原有相对位置和画面上下文；核对文案、角标、数值和空／异常态。仅改一处时优先局部修改，新版本另存。不为复用状态重复画图，只挑能说明变化的代表图。
- 静态图不能表达节奏、密度或状态变化时，按需做模拟器。先说清要验证什么，再给可调项的含义、单位、默认值、典型值和门槛两侧样例。记录确认版与正文是否一致；模拟器帮助理解，**开发和验收以确认的文字规则为准**。制作与公开发布是两件事，发布需单独授权，并核验链接能打开正确版本。

## 4. 逐模块写规则、检查并交接

- 使用主 Skill 的开发逻辑规范，按模块确认。会改变实现的待定项只阻塞相关模块，注明影响与决定方，其他内容继续。图文口径不一致先指出并确认，不自行改已定值；UI 打样值应标参考及定稿方。
- 整稿核对模块、关键边界、图文、参数和链接。没有要求的章节不补回。只有产品确认的当前规则进入最终稿；可追溯的讨论、确认依据和旧稿留在正文之外。
- 跨会话、暂停或正式交付前，给可复制的交接摘要：当前阶段／本轮范围、已确认规则及依据、最新版图文与可访问入口、阻塞项、外部处理状态、下一步。小任务几行即可。接手时不重做已完成的步骤，不把个人机器路径当成唯一入口。

## TAPD 交付

1. **准备**：明确新建、更新还是只回查；核对确认稿、正文配图和目标空间。新建先查重，更新先核对需求 ID。按实际表单核对迭代、平台、分类、涉及模块、测试方式、优先级和适用必填项。权限、关键字段或正文缺失时指出缺项，不猜、不扩大访问范围。
2. **录入与提交**：按确认稿放置文字、对应图片、附件和链接。插图受阻时保留当前表单，只交接必要步骤；恢复后先回查已填内容。提交或更新需要对应授权；若上次结果不明，先按目标 ID、详情或同名记录核查，查不到也不直接重试。只回查时不改记录。
3. **回查并询问归档**：确认需求已建档、编号和关键信息正确、正文、内嵌图、链接及约定附件都已录入，发出需求链接并主动问「是否归档到团队知识库（如 Obsidian）」。已明确授权本次归档，按主 Skill 直接归档，不重复询问。仅建档、资料未齐或结果待查，先报告缺项，不发归档确认。

把「正文已确认」「已填未提交」「提交待回查」「TAPD 已核验」「已归档」「预览已发布」「功能已上线」分别记录。每一步只报告已经核实的结果。
